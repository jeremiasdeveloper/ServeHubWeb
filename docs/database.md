# ServeHub — Database

Single SQLite database file (`db/custom.db`, `DATABASE_URL=file:…`) accessed through **Prisma** (`prisma/schema.prisma`, 16 models). All primary keys are `cuid()` strings generated by Prisma.

- Schema source: `prisma/schema.prisma` · Prisma client singleton: `src/lib/db.ts`
- Apply schema: `bun run db:push` · Seed: `bun run scripts/seed.ts` (see [development.md](development.md))

## ER diagram (text)

```
User ──1:N── Session                (session owner, cascade delete)
User ──N:1── Role                   (roleId → Role.id)
User ──1:N── Order  (createdBy)     "OrderCreatedBy"
User ──1:N── Order  (assignedTo)    "OrderAssignedTo"  (nullable)
User ──1:N── Message                (sender)
User ──1:N── Complaint (createdBy)  and (assignedTo, nullable)
User ──1:N── Attendance             @@unique(userId, date)
User ──1:N── Notification           (cascade delete)
User ──1:N── AuditLog               (nullable userId)
User ──1:N── ConversationParticipant ──N:1── Conversation

Table ──1:N── Order                 (tableId → Table.id, number unique)

Order ──1:N── OrderItem             (cascade delete)
Order ──1:N── OrderStatusHistory    (cascade delete)

Conversation ──1:N── Message                       (cascade delete)
Conversation ──1:N── ConversationParticipant       (cascade delete)
                                       @@unique(conversationId, userId)

RestaurantSetting                   standalone key/value store
AuditLog                            optional FK → User
```

Relationship notes:

- `Session`, `Notification`, `OrderItem`, `OrderStatusHistory`, `Message` and `ConversationParticipant` use `onDelete: Cascade`.
- `Order` has two relations to `User` and therefore names them explicitly (`"OrderCreatedBy"`, `"OrderAssignedTo"`). Same for `Complaint`.
- Employee "deletion" is a soft disable (`User.active = false`) — DELETE `/api/employees/[id]` never removes rows, preserving referential integrity.

## Models

### User

| Field | Type | Notes |
|---|---|---|
| `id` | String (cuid) | PK |
| `username` | String | **unique**, lowercased on create (login + API) |
| `passwordHash` | String | Argon2id hash (see [security.md](security.md)) |
| `displayName` | String | Shown in UI (avatar initials, chat, orders) |
| `email` | String? | Optional |
| `roleId` / `role` | String / Role | FK → Role |
| `active` | Boolean | Default `true`; `false` disables login and session resolution |
| `permissions` | String | JSON array of **extra** permission keys merged with role defaults; default `"[]"` |
| `lastLoginAt` | DateTime? | Updated on successful login |
| `createdAt` / `updatedAt` | DateTime | Auto |

### Role

| Field | Type | Notes |
|---|---|---|
| `id` | String (cuid) | PK |
| `name` | String | **unique** — `Administrator, Manager, Supervisor, Waiter, Kitchen Staff, Cashier, Employee` |
| `description` | String? | |
| `isSystem` | Boolean | System roles cannot be deleted |
| `permissions` | String | JSON array of permission keys (seeded from `ROLE_PERMISSIONS`) — see [roles-and-permissions.md](roles-and-permissions.md) |

### Session

`id`, `token` (**unique**, 64 hex chars), `userId` → User (cascade), `createdAt`, `expiresAt` (created + 12 h). Expired sessions are deleted lazily on the next request that presents the token.

### Table

| Field | Type | Notes |
|---|---|---|
| `id` | String (cuid) | PK |
| `number` | String | **unique** — zero-padded label (`"01"`…`"12"`) |
| `capacity` | Int | Default 4 |
| `status` | String | `AVAILABLE \| OCCUPIED \| RESERVED \| NEEDS_CLEANING` (`TABLE_STATUSES` in `src/lib/order-state.ts`) |
| `location` | String? | e.g. `Salón principal`, `Terraza` |

### Order

| Field | Type | Notes |
|---|---|---|
| `id` | String (cuid) | PK |
| `number` | Int | **unique** — sequential; API assigns `max(number, 1040) + 1` |
| `tableId` / `table` | String / Table | FK → Table |
| `createdById` / `createdBy` | String / User | Relation `"OrderCreatedBy"` |
| `assignedToId` / `assignedTo` | String? / User? | Relation `"OrderAssignedTo"`; auto-set to the kitchen user who transitions to `RECEIVED`/`PREPARING` |
| `status` | String | `DRAFT \| SENT \| RECEIVED \| PREPARING \| READY \| DELIVERED \| COMPLETED \| CANCELLED` — state machine in [orders.md](orders.md) |
| `notes` | String? | |
| `total` | Float | Server-computed from items (`price × quantity`) |
| `createdAt` / `updatedAt` | DateTime | |

### OrderItem

`orderId` → Order (cascade) · `name` · `quantity` (default 1) · `price` (default 0) · `notes?` · `status` = `PENDING | PREPARING | READY | SERVED` (default `PENDING`; informational in the MVP).

### OrderStatusHistory

`orderId` → Order (cascade) · `fromStatus` String? (null for creation) · `toStatus` String · `changedById` String? · `note` String? · `createdAt`. One row per transition, written by the order create/transition endpoints.

### Complaint

| Field | Notes |
|---|---|
| `title`, `description` | Required |
| `category` | `GENERAL \| SERVICE \| FOOD \| WAIT_TIME \| BILLING \| OTHER` (default `GENERAL`) |
| `createdById` → User | Relation `"ComplaintCreatedBy"` |
| `assignedToId` → User? | Relation `"ComplaintAssignedTo"`; assignment triggers a notification |
| `status` | `OPEN \| IN_PROGRESS \| RESOLVED \| CLOSED` (default `OPEN`) |
| `priority` | `LOW \| NORMAL \| HIGH \| URGENT` (default `NORMAL`) |
| `customerName?`, `resolution?` | Free-text customer reference and resolution notes |

### CustomerService

Support/requests register (no FK to User except `assignedToId` as a plain string). `subject`, `description`, `channel` = `IN_PERSON | PHONE | EMAIL | ONLINE`, `customerName?`, `customerContact?`, `status` = `OPEN | IN_PROGRESS | RESOLVED | CLOSED`, `assignedToId?`.

### Conversation & ConversationParticipant

- `Conversation`: `name?`, `isGroup` (default false), timestamps, and relations to `messages` / `participants`.
- `ConversationParticipant`: `conversationId` + `userId` (**composite unique** `@@unique([conversationId, userId])`), `lastReadAt?`. Chat access control is participant-based (`403` for non-participants).

### Message

`conversationId` → Conversation (cascade) · `senderId` → User · `content` · `createdAt`. Ordering is chronological; the API reads the latest 500.

### Attendance

`userId` → User · `date` **String** `YYYY-MM-DD` · `checkIn?` · `checkOut?` · `status` = `PRESENT | ABSENT | LATE | HALF_DAY | LEAVE` · `notes?`. Composite unique `@@unique([userId, date])` enforces one record per person per day.

### Notification

`userId` → User (cascade) · `type` = `ORDER_READY | NEW_ORDER | NEW_MESSAGE | COMPLAINT_ASSIGNED | SYSTEM` · `title` · `body` · `data` (JSON string with extra context, e.g. `{"orderId":"…"}`) · `read` (default false) · `createdAt`. Created by order/chat/complaint side effects; per-user queries only.

### RestaurantSetting

Simple key/value store: `key` (**unique**) · `value`. Seed creates `restaurant_name` and `restaurant_id`. Managed via `GET/PATCH /api/settings`. A `servehub_config` key is the planned (not yet wired) override for the runtime config — see [configuration.md](configuration.md).

### AuditLog

`userId?` → User (nullable, set null on user deletion is not configured — user rows are never hard-deleted) · `action` (e.g. `LOGIN`, `ORDER_CREATE`, `ORDER_READY`, `TABLE_UPDATE`, `EMPLOYEE_DISABLE`, `ROLE_UPDATE`, `COMPLAINT_UPDATE`, `CS_CREATE`, `SETTINGS_UPDATE`) · `entity?` · `entityId?` · `details?` (e.g. `DRAFT->SENT` for transitions) · `ip?` (not populated in the MVP) · `createdAt`. Written by all mutating endpoints — see [security.md](security.md).

## Indexes & uniqueness summary

| Model | Constraint |
|---|---|
| `User.username`, `Role.name`, `Session.token`, `Table.number`, `Order.number`, `RestaurantSetting.key` | unique |
| `ConversationParticipant (conversationId, userId)` | composite unique |
| `Attendance (userId, date)` | composite unique |
| Implicit | SQLite indexes back every unique constraint and Prisma FK; list endpoints sort by `createdAt desc` (orders/complaints/CS/notifications) or `number asc` (tables) and are capped (200/500/100 rows) |

SQLite stores JSON arrays as plain `String` columns (`Role.permissions`, `User.permissions`, `Notification.data`); the API parses/serializes them with `JSON.parse`/`JSON.stringify` guarded by try/catch.
